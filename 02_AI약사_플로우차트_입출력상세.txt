개념 요약만 하면:
  질문·자동완성 → 약이름 확정·공식검색 → 쉬운 답

설계 문서 본체는 반드시:
  1) 앱이 무엇을 보내는가 (IN)
  2) 서버가 무엇을 불러오는가 (CALL)
  3) DB에 무엇을 읽고/쓰는가 (READ/WRITE)
  4) 앱이 무엇을 받아 어디에 보여주는가 (OUT)

--------------------------------------------------------------------------------
1. 앱이 보내는 것 (IN)
--------------------------------------------------------------------------------

화면: lib/features/drug_explain/... (약 설명·채팅)

(1) 자동완성
    GET /api/v1/drug-explain/suggestions
    쿼리:
      q         입력 글자 / 초성 / 빈값(초기 FAQ·오늘약)
      user_id   오늘 먹는 약 후보용

(2) 채팅 질문
    POST /api/v1/drug-explain/chat
    body:
      user_id   사용자
      message   예: "타이레놀 뭐에 좋아?"
                 "타일레놀" (오타)
                 "아스피린 부작용"

(3) (선택) 약 카드 설명
    GET /api/v1/drug-explain/{medicine_code}

--------------------------------------------------------------------------------
3. DB READ / WRITE
--------------------------------------------------------------------------------

■ READ (상담 시 주로 읽기)

  mfds_drug_permission.db
    - 제품명 검색 (search_permission_names / find_permission_product)
    - 상세 미러 (detail_synced 등)

  alkongyakong.db
    - SELECT … FROM medicines WHERE product_name …
    - 오늘약/등록약: user_medicines (+ schedules) 기반 suggestions

  easy_category_map.db
    - SELECT trigger, link_type, link_value FROM chat_links …
    - SELECT official_phrase, easy_label … FROM category_map …

■ WRITE (현재)

  - 채팅 질의·응답 이력 테이블 저장은 아직 로드맵(미구현)
  - 상담 자체는 읽기 중심. OCR 등록 약이 lexicon/오늘약으로 읽혀 들어옴

  → 문서에 "WRITE 없음"을 숨기지 말 것. 지금은 READ + 외부 API + LLM.


--------------------------------------------------------------------------------
4. 앱이 받는 것 / 어디로 보여주는가 (OUT)
--------------------------------------------------------------------------------

suggestions 응답
  { items: [ { label, type: medicine|faq|phrase|… }, … ] }
  → 입력창 아래 자동완성 칩

chat 응답
  {
    ok: bool,
    reply: string,           // 말풍선
    candidates?: [           // 0.75~0.90 애매할 때
      { label, score }, …
    ],
    trace: {                 // 내부/디버그 (화면 기본 비노출)
      original, corrected, source, stage, …
    }
  }

앱 화면 분기
  candidates 있음 → "혹시 이 약인가요?" 선택 UI
  ok=true         → reply 표시
  ok=false        → 못 찾음 / 자료 부족 안내
  선택 후 재전송  → 확정 약이름으로 다시 chat


--------------------------------------------------------------------------------
5. ★ 공통으로 끝까지 흐르는 값
--------------------------------------------------------------------------------

  교정·확정된 공식 약이름 (corrected / product_name)
  + official.source_text (효능·용법·주의 근거)

  흐름:
    앱 message/칩
      → spell/match로 이름 확정
      → retrieve로 source 확보
      → fixed 또는 generate+guard
      → 앱 reply


--------------------------------------------------------------------------------
6. 단계별 입·출력을 글로 풀면
--------------------------------------------------------------------------------

  (1) IN   어르신이 "타일레놀" 입력 또는 칩 터치
  (2) CALL suggestions / 허가DB / 오늘약 → 후보 목록
  (3) IN   "타이레놀 뭐에 좋아?" POST chat
  (4) CALL spell→match→retrieve
  (5) CALL fixed DB답 또는 Gemini(근거만)→guard
  (6) OUT  짧은 쉬운 reply / 또는 후보칩 / 또는 안전 안내


--------------------------------------------------------------------------------
7. 로드맵에서 WRITE가 붙을 자리
--------------------------------------------------------------------------------

  [단기] chat_logs INSERT (user_id, message, reply, corrected, source, stage)
  [단기] OCR 직후 약 → 채팅 프리필
  [중기] DUR 결과 문장과 chat reply 연결


--------------------------------------------------------------------------------
8. 사용자에게 이 구조가 주는 것
--------------------------------------------------------------------------------

  물어보면(IN)
  공식 자료를 찾아(CALL/READ)
  쉽게 답하고(OUT)
  애매하면 고르게 한다(candidates).

  목적: 손·오타가 서툴어도, 거짓 정보 없이 복약 상담.
