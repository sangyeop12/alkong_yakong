--------------------------------------------------------------------------------
0. 이 기능이 왜 필요한가
--------------------------------------------------------------------------------

어르신(환자)이 약국·병원에서 받은 처방전/복약안내문을
손으로 약 이름·횟수·일수를 일일이 치지 않아도,
사진 한 장으로 "지금 먹어야 할 약"을 앱에 등록하기 위해서다.

구체적으로는 아래를 자동화한다.

  1) 약 이름 읽기          → 내 약함에 등록
  2) 하루 몇 번 / 며칠분   → 복약 알람 스케줄 생성
  3) 복용법·효능 설명      → 어르신용 쉬운 설명 카드
  4) 공식 약품 코드 연결   → 함께먹기(DUR) 검사 등에 사용

OCR이 없으면 글자를 못 읽는 어르신·보호자가
약 이름을 직접 타이핑해야 해서, 처방전 등록 관문이 막힌다.


--------------------------------------------------------------------------------
1. 한눈에 보는 흐름 (어디서 들어와 어디로 나가는가)
--------------------------------------------------------------------------------

[앱 Flutter — 처방전 찍기 화면]
  사진 촬영 또는 앨범에서 고르기
    ↓
  이미지를 base64 문자열로 변환
    ↓
  POST /api/v1/prescriptions/ocr
    보내는 것(IN):
      - user_id
      - image_data  (사진 base64)
      - source_type ("OCR")

[백엔드 FastAPI]
  create_prescription_from_ocr()
    │
    ├─ ① engine (gemini-vision)
    │     IN : 이미지 bytes
    │          (너무 큰 휴대폰 사진은 JPEG로 줄인 뒤 전송)
    │     OUT: raw_text
    │          = 사진에 보이는 글자를 그대로 옮긴 원문 문자열
    │
    ├─ ② parser (gemini JSON 구조화)
    │     IN : raw_text
    │     OUT: structured (정형 JSON)
    │          - hospital_name, pharmacy_name, prescribed_date
    │          - items[]  (약별 필드)
    │          - field_coverage (필드 채움률 %)
    │     + filter_to_source
    │          원문에 없는 약이름·숫자를 추측값으로 넣지 못하게 걸러냄
    │
    ├─ ③ medicine resolve (약품 매칭)
    │     IN : 각 item.drug_name
    │     OUT: medicine_code + match_status
    │          - 허가정보 DB / e약은요 등에서 공식명 매칭
    │          - 실패해도 OCR-임시코드(UNMATCHED)로 남겨
    │            확인 화면까지는 진행
    │
    └─ ④ DB 저장 후 JSON 응답
          저장:
            prescriptions         ← 처방전 헤더 + ocr_text(raw 원문)
            prescription_items    ← 약별 용량/횟수/일수/해설
            user_medicines        ← 내 약함
            medication_schedules  ← 알람 시각
          응답(OUT) → 앱:
            prescription_id, ocr_status, ocr_text, ocr_trace,
            items[] (drug_name, medicine_code, match_status,
                     frequency_per_day, duration_days,
                     easy_explanation, uncertain 등)

[앱 Flutter — 이렇게 읽었어요 화면]
  items[] 를 카드로 보여 줌
  → 사용자가 "이대로 등록하기" 확인

2. 필드별로 — 무엇을 뽑아서 어디에 넣는가
--------------------------------------------------------------------------------

[뽑는 값]                    [어디서]              [어디로 들어감]                 [앱에서]
----------------------------------------------------------------------------------------------
raw_text                     이미지 전체 글자       prescriptions.ocr_text         화면엔 거의 안 보임
                                                     (재처리·디버그용)

hospital_name                병원/의원명            prescriptions.hospital_name    거의 미사용
pharmacy_name                약국명/조제약사        prescriptions.pharmacy_name    거의 미사용
prescribed_date              조제·처방 일자         prescriptions.prescribed_date  스케줄 시작일 참고

drug_name                    약 표의 약품명         prescription_items.ocr_drug_name
                                                     + medicines 매칭               카드 제목

dosage                       1회 투약량             prescription_items.dosage      복용 안내 보조
frequency_per_day            1일 투여횟수           items + medication_schedules   "하루 N번"
duration_days                투약 일수              items + 스케줄 기간             "N일"
easy_explanation             복용법/효능 설명칸     prescription_items.            카드 아래 쉬운 설명
                                                     easy_explanation

medicine_code                매칭 결과              medicines / user_medicines     DUR·내 약 연결
match_status / uncertain     매칭 품질              응답 JSON                      "확인 필요" 표시


※ 현재 스키마에서 안 뽑는 것
  - 환자 이름, 나이/성별, 교부번호, 병원 전화
  → 복약 등록·알람에 당장 필수는 아니라 제외해 둠


--------------------------------------------------------------------------------
3. 정형 스키마 (구조화가 맞추는 틀)
--------------------------------------------------------------------------------

헤더:
  - hospital_name   (문자열)
  - pharmacy_name   (문자열)
  - prescribed_date (YYYY-MM-DD 권장)

약 항목 items[] 각 원소:
  - drug_name          (필수)
  - dosage             (문자열, 예: "0.50")
  - unit               (정/캡슐 등, 원문에 있을 때만)
  - frequency_per_day  (정수, 하루 몇 번)
  - times_per_take     (정수, 한 번에 몇 개)
  - duration_days      (정수, 며칠분)
  - easy_explanation   (쉬운 설명)
  - warning_note       (주의사항)

표 형식 복약안내일 때 열 매핑:
  약품명 및 용량  → drug_name (+ dosage/unit)
  1회 투약량      → dosage 또는 times_per_take
  1일 투여횟수    → frequency_per_day
  투약 일수       → duration_days


--------------------------------------------------------------------------------
4. "필드 채움 커버리지" 가 뭔가 / 인식률과 뭐가 다른가
--------------------------------------------------------------------------------

■ 필드 채움 커버리지 (field_coverage)
  - 의미: 구조화 결과 JSON에 핵심 칸이 "비지 않고 채워졌는지"의 비율
  - 정답과 비교하지 않음. "칸을 채웠다"만 봄
  - 계산 대상:
      헤더 3칸 (hospital_name, pharmacy_name, prescribed_date)
      + 약마다 6칸 (drug_name, dosage, unit, frequency_per_day,
                    times_per_take, duration_days)
  - 예: unit·times_per_take 가 원문에 없으면 비는 것이 정상
        → overall 100%가 나오기 어려움

■ 정답 대비 인식률 (ground-truth accuracy)
  - 의미: 사람이 사진에서 확인한 정답과 비교해 맞았는지
  - 이 문서 기준 정답 항목 19개:
      헤더 3
      + 약 이름 검출 4
      + 약별 (dosage, frequency_per_day, duration_days) 12
  - "실제로 맞게 읽었나"를 보는 지표

6. 단계별 입·출력을 글로 풀면
--------------------------------------------------------------------------------

(1) 들어옴
    앱이 찍은 처방전 사진 → base64 → 서버 API

(2) 글자 읽기 (engine)
    사진 → "조제약 & 복약안내 … 프리마라정 … 0.50 | 3 | 7 …" 같은 긴 글자뭉치(raw_text)

(3) 칸에 나눠 담기 (parser)
    긴 글자뭉치 →
      병원칸, 약국칸, 날짜칸,
      약1 이름/용량/횟수/일수/설명,
      약2 … 약4 …
    원문에 없는 값은 넣지 않음(필터)

(4) 약 이름 공식 DB에 연결 (resolve)
    "프리마라정" → medicine_code (있으면 MATCHED, 없으면 OCR-임시 UNMATCHED)

(5) 저장소에 심음 (DB)
    처방전 1장 헤더
    + 약 줄마다 prescription_items
    + 내 약함 user_medicines
    + 알람 medication_schedules

(6) 나감
    서버가 items JSON을 앱에 돌려줌
    → "이렇게 읽었어요" 카드
    → 사용자 확인 후 등록 완료


--------------------------------------------------------------------------------
7. 참고 / 한계
--------------------------------------------------------------------------------

- OCR 엔진·구조화 모두 Gemini API(GEMINI_API_KEY)에 의존한다.
- 무료 할당량이 소진되면 quota_exceeded 로 실패할 수 있다.
- 인식률 숫자는 "이 한 장(20260825_164345.jpg)" 기준이다.
  다른 처방전(흐림·접힘·손글씨)에서는 달라질 수 있다.
- 환자 이름 등 개인정보는 현재 파이프라인에서 의도적으로 안 뽑는다.
