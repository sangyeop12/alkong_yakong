1. 어디에 무엇이 들어오는가 (IN)
--------------------------------------------------------------------------------

입력                 출처                         이 게이트에서의 역할
------------------  ---------------------------  ---------------------------
message             POST drug-explain/chat       오타교정·FAQ종류·생성 질문
q                   GET suggestions              초성/부분검색·chat_links
lexicon             suggestions 결과 약이름      matcher 사전
raw_text            OCR engine 출력              filter_to_source 정답지
parsed items        OCR parser 초안              원문 없는 필드 삭제 대상
source_text         retrieve_official            guard·generate 근거
medicine fields     efficacy/usage/precautions   fixed_db_reply 재료


--------------------------------------------------------------------------------
2. 서버가 불러오는 것 (CALL) — 게이트별
--------------------------------------------------------------------------------

■ 오타·이름 교정 (B)

  CALL                         하는 일
  ---------------------------  --------------------------------
  spell.extract_…              약이름 후보만 (STOP_WORDS 제거)
  name_matcher                 0.90 확정 / 0.75~0.90 후보
  search_permission_names      허가DB로 lexicon 보강
  retrieve_official            공식 제품·source_text
  suggestions + chosung        초성·일상어→약검색
  lookup_chat_links            easy_category_map.db 연결어


■ 환각 방지 (A)

  CALL                         하는 일
  ---------------------------  --------------------------------
  filter_to_source             OCR 환각 제거
  retrieve 실패 시 생성 스킵   추측 답 금지
  _fixed_db_reply              LLM 없이 DB 필드만
  generate_from_source         source_text만 프롬프트에 투입
  guard_reply                  문장별 근거 overlap
                               답의 숫자가 source에 있는지 검사
  _official_excerpt_reply      가드 실패 시 원문 발췌


■ 쉬운 언어 (C)

  CALL                         하는 일
  ---------------------------  --------------------------------
  validate_easy_output         문장 수·길이 제한 (너무 긴 문장 거절)
  lookup_easy_label            공식표현→쉬운 괄호
  format_display_name          "약이름 (열나약)"
  Flutter 시니어 카피          "읽는 중" 등 기술용어 회피


--------------------------------------------------------------------------------
3. DB READ / WRITE
--------------------------------------------------------------------------------

■ READ

  mfds_drug_permission.db     이름 검색·공식 상세 → source
  alkongyakong.db medicines   로컬 공식/등록 약
  user_medicines              오늘약·lexicon
  easy_category_map.db
    category_map              쉬운 분류
    chat_links                일상어→검색어/FAQ

■ WRITE

  - 이 세 게이트(가드·교정·쉬운말) 자체는 보통 INSERT 없음
  - OCR 경로의 filter 결과는 이후 prescription_items 등으로 WRITE됨
    (환각 걸러진 뒤의 값만 저장된다는 점이 중요)
  - 채팅 가드 결과 로그 WRITE는 로드맵(미구현)

6. 수용 시나리오 (IN → OUT이 맞는지)
--------------------------------------------------------------------------------

시나리오 IN                         기대 OUT
----------------------------------  --------------------------------
"타일레놀"                          후보칩 또는 타이레놀 확정
                                    (없는 약 이름 발명 없음)

"타이레놀 효능" + 공식자료 있음     ok=true, 쉬운 2~3문장
                                    source에 없는 용량 문장 없음

존재하지 않는 약이름                "공식 자료에서 찾지 못했어요"
                                    LLM 추측 답 없음

OCR "| 0.50 | 3 | 7 |"              frequency=3, duration=7 유지
                                    (표 숫자 필터 통과)

유사도 0.80대                       candidates만, 자동확정 금지


--------------------------------------------------------------------------------
7. 세 게이트가 빠질 때 (왜 IN/CALL/OUT으로 적어야 하나)
--------------------------------------------------------------------------------

  환각방지 없음
    IN은 같아도 OUT에 거짓 용량/부작용이 나감 → 위험

  오타교정 없음
    CALL이 약을 못 찾음 → OUT이 항상 실패

  쉬운말 없음
    OUT이 허가문 원문 덤프 → 어르신이 이해 못 함

  그래서 "세 원 겹침"만 그리지 말고
  각 게이트의 IN / CALL / OUT을 표로 적는 것이 맞다.


--------------------------------------------------------------------------------
8. 사용자에게 이 구조가 주는 것
--------------------------------------------------------------------------------

  틀린 말을 막고(A)
  철자가 틀려도 약을 찾아 주며(B)
  쉬운 말로만 들려 준다(C).

  목적: 안전하고, 찾을 수 있고, 이해할 수 있는 복약 안내.
